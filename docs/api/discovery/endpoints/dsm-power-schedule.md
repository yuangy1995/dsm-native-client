# DSM 电源计划内部 API

## 当前范围与证据

稳定标识 `dsm-power-schedule`，组件 `dsm-core`，内部混合读写能力，风险 `high`。
macOS 支持开机/关机计划的新增、编辑、启停、移除和整体保存。用户已要求开放供测试，
不再设置仅因没有实测而固定关闭的门槛；权限、完整清单、确认和结果核查保留。

2026-10-02/03 在 DSM 7.2.1-69057 Update 12 官方页面核对列表与编辑结构；保存参数
来自官方前端 static 证据，**没有创建、保存或触发真实电源计划**。设备匿名归属待确认，
不提升旧 lab-a 记录。已有 2026-09-26/27 读取证据仍独立保留。

## 请求与响应

| 方法 | API / 版本 | 参数与结果 |
| --- | --- | --- |
| 读取 | `SYNO.Core.Hardware.PowerSchedule.load` v1 | 无业务参数；`poweron_tasks[]` 与 `poweroff_tasks[]` |
| 保存 | 同 API `save` v1 | 两个完整数组，空数组用于移除该类全部计划 |

路径和请求格式由 `SYNO.API.Info` 发现，使用既有 POST 会话构造器。

每项字段：`enabled:Boolean`、`weekdays:String`（数字 CSV，周日=0、周六=6）、
`hour:Int(0...23)`、`min:Int(0...59)`。每天归一为 `0,1,2,3,4,5,6`。
官方前端上限为 **200 条**，不再沿用旧客户端 128 条截断上限。时间是 NAS 本地时钟，
不转换为 Mac 时区；服务端缺失时区时不根据 Mac 猜测。

## 整体保存与安全

- 编辑在本地形成草稿；新增、勾选、编辑或从草稿移除都不会立即写 NAS。
- 只有两个独立数组同时存在、所有条目完整且不超过 200 条，才允许整表保存。旧
  `schedules/items` 摘要仍可读取，但不能作为整表覆盖依据。
- 当前可编辑动作只有开机与关机，规则为每天/每周。一次性、重启、未知动作、未知
  启用状态、非法时间或不完整条目不得被保存流程静默删除。
- 任意条目在同一时分与重叠星期均拒绝，即使动作不同或其中一条停用；与官方编辑器一致。
- 保存确认明确说明计划会使 NAS 无人值守关机、相关服务会中断。
- 提交前复读完整清单并与初始基线做语义比较，忽略临时 ID、数组顺序和星期顺序；
  他处发生变更时拒绝覆盖。客户端每次仅发送一个 save，不并行保存、不自动重试。
- 提交后复读两个数组，完整清单必须与目标一致才确认成功。未知结果保留刷新门闩，
  失败刷新不能解除；再次保存须基于成功刷新后的当前清单。
- 空清单页仍提供添加入口；未知或不完整清单明确解释为何不能覆盖，并给出刷新/DSM 路径。

## 五端影响

- macOS：原生草稿、星期/时分选择器、启用切换、风险确认、刷新和五态显示。
- 共享 Apple：新增 `NasPowerScheduleSnapshot.supportsEditing`（默认 false）和带默认不支持
  实现的 Repository 保存方法，保持旧实现源码兼容；没有存储格式变化。
- iPhone/iPad：M6a1 已接读取，M6c1 已增加完整移动草稿与保存恢复，当前验收进度见下节。
- Windows/Android：本轮未修改。Windows 原有 128 条只读实现需要后续同步上限和语义；
  两端若实现保存必须完整采用本记录，不能把摘要逐条直接写回。

## 验证与未验证项

正式自动化位于 `DsmNasAdministrationRepositoryTests`、`NasAdministrationModelTests`，
覆盖两个数组（含清空）、周日编码、禁用条目、重叠/数量上限、并发基线变化、未知条目
零写入、提交断线、回读不符和重复提交。Schema：
`contracts/schemas/nas-hardware-editing.schema.json`；请求样本：
`contracts/request-fixtures/hardware/save-power-schedule/`。

`PENDING_USER_VALIDATION`：由用户在无任务冲突的维护时段新建一条**停用**计划，保存并在
DSM 核对时间与星期，再编辑/移除并核对清单；确认正确后才安排真实开关机测试。夏令时、
系统休眠/UPS、无自动开机硬件与其他 DSM/权限组合尚未验证。只回传脱敏步骤、版本与错误。

历史 lab-a 的 2026-07-31 只确认方法名与候选读取，保持 static；本轮没有写行为验证。

## 2026-10-05 移动 M6a1 接入

iPhone/iPad M6a1 已接计划读取、启用状态筛选、NAS 当地时间/星期及截断提示；未知启用状态不归为停用。新增/编辑/保存继续在 M6c 实施，实施后按能力、完整快照、确认、防重复和结果恢复开放；当前没有新增移动写请求。当前环境命令与两端页面验证集中在[移动主计划](../../../development/APPLE_MOBILE_MACOS_PARITY_DEVELOPMENT_PLAN_ZH.md#m6a1-五项读取与筛选)及其验证历史；真实 NAS 证据不提升。

## 2026-10-06 移动 M6c1 管理接入

移动端已增加完整清单草稿内的新增、编辑、启停、移除、还原与整体保存，空清单保留编辑入口；iPhone/iPad 均采用原生表单和独立条目编辑器。时分是 NAS 当地时间，不通过设备时区换算。沿用两个完整数组、200 条上限和星期/时分冲突校验，停用条目仍不能重叠；摘要或截断响应不会变为可覆盖的完整清单。

共享管理入口复用旧 Mac 的原请求编码，保存前按语义比较原清单及 NAS 时区，忽略临时 ID 与返回顺序；确认的完整目标与时区一起生成恢复摘要。保存后若 NAS 时区变化，不能仅因时分相同就报告全部成功。写前权限与落盘、接受回执和完整读取分别记录；提交断线及 App 重启只读恢复，不重复发送 save。记录不保存时分、星期或时区正文，不迁移登录资料。

本机行为测试、共享/Mac 回归与两端实际 UI 已有通过证据，命令和逐轮结果以[移动 M6c1 账本](../../../development/APPLE_MOBILE_MACOS_PARITY_DEVELOPMENT_PLAN_ZH.md#m6c1-内存压缩与电源计划)为准；未执行真实计划保存或开关机，不提升历史证据。Windows/Android 尚需独立同步完整清单、200 条上限和相同恢复语义，本片不改代码。
